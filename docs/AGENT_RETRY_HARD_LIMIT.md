# Agent任务重试：服务端强制一次上限

## 为什么需要服务端硬约束

之前的 Agent 故障恢复建议模块（PR #28）只建议「手动重试至多一次」，但实际任务接口可不断对新的重试任务点击重试，形成无限任务链、重复消耗模型资源。因此本阶段将这条建议升级为 SQLite **持久化硬约束**。

## 服务端规则

1. 每个原始任务最多创建一个**人工重试任务**，关系保存在 `web_task_retries(original_id,retry_id)`。
2. 同一原始任务重复点击或并发点击，复用已有回执和任务ID，不创建新任务。这一行为保持兼容。
3. 对已经是重试任务的ID再次请求 `POST /api/generation-tasks/{id}/retry`，SQLite拒绝插入第二层关系，Web API返回 **HTTP 409**（「每份任务最多允许一次人工重试」）。
4. 通过SQLite触发器 `limit_task_retry_depth` 检查，而不是只依赖页面按钮/前端的次数提示。SQLite的 `BEGIN IMMEDIATE` 事务串行化同一数据库的并发重试，触发器失败时新任务创建与关联事务一并回滚，不留下孤儿任务。
5. 触发器也禁止自己指向自己、以及两个独立原任务共用同一个重试ID的别名关系。安装是 `CREATE TRIGGER IF NOT EXISTS`：不删除、迁移或重建既有数据；已有老数据保留，但新增关系受限制。
6. 正在排队/执行、试用空间的活动任务及总配额、知识库删除、来源文件移除、会话隔离等既有约束**保持不变**。这些限制可能早于次数上限返回409或429。
7. 原生本地Web API和独立浏览器试用空间均在建表时安装触发器；两类接口都将 `task_retry_depth_limit` 错误映射为不暴露数据库详情的409。
8. 不自动重试，不改变用户手动确认流程，不读取模型生成的工具名或执行模型指令。

## 离线验收（非Qwen实测）

使用真实HTTP路由、当前访客的真实SQLite连接及固定模拟任务终态：

- 初次失败→人工重试创建一次→再次点击原任务复用回执。
- 第一次重试任务也失败→第二层重试返回409，数据库仍仅有2个任务和1条重试关系。
- 3个HTTP客户端同时点击同一个原任务，验证一致回执与没有重复入队；随后同时尝试第二层重试，一律拒绝。
- 另一个访客不能借任务ID重试或查看对方任务。
- 使用SQL直接尝试绕过限制、引入任务别名关系，都被数据库拒绝。
- 重启后触发器与重试回执保持存在。

### 未完成的真实验收

GitHub CI不连接用户实体设备或本地Ollama/Qwen；上述测试不代表真实模型超时分布、token费用、内存峰值、完整交互体验或 Android 端联调。用户恢复电脑后再进行真实故障注入。

## 是否需要新Skill？

不需要。次数限制是数据完整性和确定性任务调度规则，必须由服务端数据库控制；把它做成Skill反而增加绕过安全约束的风险。
