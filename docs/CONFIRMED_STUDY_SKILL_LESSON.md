# 第六关：用户确认后执行 Agent 复习 Skill

本实验叠加 [PR #19](https://github.com/rxy5787-source/zhixueban-agent/pull/19) 的只读BKT学习计划，仍处在独立开发分支。
目标是让用户先看到计划与历史资料，再明确确认，才创建任务。

## 数据流

1. 浏览器通过签名会话Cookie访问自己的试用空间。
2. `GET /api/study-plans/{library_id}` 返回BKT计划、版本摘要 `revision`，以及该空间该知识库中以前上传、尚未移除的资料。
3. 用户在“学习分析”页面选择原始资料和1–3道题，点击“确认并生成复习题”。
4. `POST /api/study-plans/{library_id}/execute` 验证会话、计划版本、库和资料归属、文件有效性、模型可用性及任务配额。
5. 白名单 `queue_practice` Skill 在事务中创建现有 `jobs` / `web_tasks` 任务。后续由现有Worker、Qwen和原文证据校验链运行，系统不自行绕过质检。
6. `clientRequestId` + 计划指纹防止重复提交；重试使用同一个标识可以找回原任务。

## 安全与边界

- 读写都只发生在当前签名会话映射的 `TrialStore`；不接受客户端指定的数据路径或用户身份。
- Planner只给出诊断/定向/综合三种建议，不执行模型给出的任意函数名。
- 依据由已有BKT结果决定，复习目标知识点作为**数据**进入提示词，不能作为模型指令执行。生成题目仍必须经过原有资料支持的质检。
- `revision` 在确认时重新计算：答题记录改变或规划状态改变时，返回409要求刷新。
- 不自动更改BKT，只有用户完成练习提交答案才更新掌握度。
- 没有原始上传资料时只显示“请先上传资料”，不能凭空创建有原文证据的题目。
- 并发和容量仍受原Web试用限制；不能宣称完成生产级端到端运行。

## 手动验证

1. 运行本地Web试用版，并打开一份包含SQL原文的知识库。
2. 提交几道练习后，进入“学习分析”查看Agent建议。
3. 选择已有资料，确认生成1–3题；检查创建的任务、出题进度、模型复核和归档。
4. 重放完全相同的请求标识，确认返回原任务；修改学习数据后，旧 `revision` 应拒绝。
5. 两个浏览器空间中即使都叫SQL，也不得互相读取或执行对方的资料。
